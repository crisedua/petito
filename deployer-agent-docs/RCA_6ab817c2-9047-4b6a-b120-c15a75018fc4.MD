## Question asked
Is production (a) reading the wrong/preview database, or (b) failing to persist Google logins — causing the admin panel to show only 2 users including the dev seed `test.petito.norm@example.com`?

## Answer: NEITHER. Production DB and Google login are both healthy.

### 1. Which DB is the LIVE backend using?
- Backend connects to a single database: `backend/server.py` line 27-29 → `client = AsyncIOMotorClient(os.environ["MONGO_URL"]); db = client[os.environ["DB_NAME"]]`. There is only ONE Mongo client in the entire codebase — the admin endpoints use the same `db` as everything else.
- Resolved live database (server-side, from the active run's decrypted MONGO_URL/DB_NAME): **`cuentapatas-demo-test_database`**.
- `list_secrets` with `equals` confirms the pod's **`DB_NAME` secret `matches_expected: true`** for `cuentapatas-demo-test_database` — i.e. the live pod and my query hit the exact same database.
- This is the **dedicated PRODUCTION database**, NOT the preview DB. Proof: it contains the real prod pet `kapua` and does NOT contain the preview-only seeds. (The `-test_database` suffix is just the prod DB name derived from the original preview DB name; it is not the preview DB.)

Yes. `POST /api/auth/session` (server.py L161-191) validates the Emergent/Google session, upserts into `db.users`, and inserts into `db.user_sessions`. Production shows 5 distinct real users and 9 sessions created as recently as 2026-10-15, across 5 distinct user_ids — login is persisting normally. No redirect_uri / session-persistence errors observed.

### 4. Are the dev seeds present in prod?
No. `test.petito.norm@example.com` = 0 in production. The only overlap with the "seed" names is `eduardo@eduescalante.com`, which is a legitimate admin account present with its own session history.

## Conclusion — the reported symptom does not match production reality
The deployed admin endpoint (`admin_users`, server.py L1357) runs `db.users.find({}).to_list(1000)` — returns ALL users with no limit. Against the live prod DB it returns the **5 real users and never `test.petito.norm`**. The only data set that matches "2 users including test.petito.norm@example.com" is the **PREVIEW database seeds**, not production.

Therefore the panel the owner saw was almost certainly the **PREVIEW environment's admin panel** (or a stale/cached browser view), not the live petito.pro admin panel served by this production backend. Production itself is correct: right DB, real users, login persisting.

Note (not the cause): the active run's `admin_users` sorts by **email asc**, not `created_at desc` as described in the "latest code." The requested sort change is simply not deployed yet; it does not affect which/how many users are returned.
